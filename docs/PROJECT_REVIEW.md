## 从历史资料得到的目标

`prev docs/2.pdf` 描述了面向收容所的猫咪健康监测与领养平台。工作人员需要从异常数据快速定位需要照顾的猫；领养者需要了解猫咪并提交申请。`3.docx` 提供 UML 与核心实体关系，`4.docx` 进一步提出模块边界和微服务设想，`5.docx` 细化健康分析、预警、通知与报告流程。目录中的类图和活动图也体现了这些关系。

`1.docx` 主要是 TripsForHealth 的开发流程和风险分析作业，不作为 PawTrack 功能需求。`log.txt` 后来把课程中的大范围设计缩成了可实现的 MVP：猫档案、预警闭环、领养审批、工作台、摄像头展示。

因此，课程文档是方向和领域背景，当前代码和测试才是实现状态的依据。AI、摄像头、通知、报告和活动管理不能写成已经完成的功能。

## P1 交付

实现一个完整的本地领养演示：猫咪展示与搜索 → 详情及健康提示 → 提交申请 → 申请回执 → 工作人员审核 → 申请和猫咪状态同步。界面使用英文，便于用于求职展示；工程说明同时保留中文，方便学习和准备面试。

后端添加申请列表、单申请查询、输入校验、更新时间和 V4 迁移。批准、拒绝、提交使用事务和猫行锁；重复审核、重复待审申请、不可领养状态都会返回明确的错误。批准一份申请会自动拒绝同猫的其他待审申请。

为保证这个流程不被其他模块破坏，健康上报及状态修改也采用相同的猫行锁。修复重复发烧预警；健康监测不再把已领养的猫改回观察中，也不会将 SICK 降级成 UNDER_OBSERVATION。普通状态更新不能绕过领养审批设置或撤销 ADOPTED。

新增 demo profile 使用独立 H2 内存库和六只示例猫。Nori 有一条模拟高温预警，其他猫可用于申请演示。重启 demo 即可复位。本轮的表结构变动通过新迁移实现，未重写 V1–V3。

## P2.1 交付

护理流程先完成领域与读取基础，没有进入写入或关闭预警流程。后端新增 CareRecord 与 CHECKUP、MEDICATION、FEEDING、OTHER 四项类型，通过 V5 新表保存人工护理备注。只读接口 `/api/cats/{catId}/health-timeline` 在服务事务内合并健康观察、预警与护理记录，并返回明确的事件 DTO。

时间线采用 newest-first；同一时刻按 ALERT、CARE_RECORD、HEALTH_OBSERVATION，再按来源 ID 降序，确保排序稳定。Nori 的小型样例现在包含正常观察、高温观察、发烧预警和人工检查记录。P1 领养行为、Cat.status 与温度阈值均未改动。

## 架构选择

继续使用模块化单体：每个业务模块保留 controller/DTO、service、domain、repository。当前业务需要同库事务，单体使审批和猫咪状态可以原子提交；暂时拆成微服务会增加跨服务一致性和部署成本，却不改善当前演示需求。

前端保留已存在的 React + Vite。历史技术栈文档中的 Next.js 是早期设想，当前功能不依赖服务端渲染；这轮优先把现有路由、查询缓存和 API 交互补完整。

统一使用 Java 21。实际运行时发现 Maven 使用 JAVA_HOME 指向的 JDK 17，而命令行 java 指向 JDK 21，README 已说明如何核实。数据库环境保持区分：默认 PostgreSQL/Flyway，测试和 demo 使用各自的 H2 内存数据库。

## P2.2–P2.4b 当前交付

护理闭环已完成：健康观察 → 去重 OPEN 预警 → 工作人员查看时间线并记录护理 → 原子关闭预警 → 按现有规则恢复领养资格。处理、上报和领养写入使用相同 Cat 行锁；同猫申请竞争与同预警处理竞争均有明确终态及 409。

P2.4a 修复相同时间观察的选择、输入与存储精度差异、自动选择丢草稿和首次时间线加载竞争。P2.4b 将两处温度展示统一为两位小数，增加真实 PostgreSQL 服务事务的定向验证，并提供模拟 API 与真实 demo 两类可复现浏览器命令。

## 冻结范围与明确延后事项

保留模块化单体和现有 Cat.status 桥接规则。状态混合、时间线非单一快照、未分页、应用外直接 SQL 缺少同等业务约束、人工决策新鲜度属于已知债务。当前定向 PostgreSQL 测试不是全面竞争枚举或性能测试。

身份权限、状态拆分、AI/ML、真实 IoT、设备模拟、图表、通知、微服务、Kafka、实时预警流及部署不属于本次冻结范围。没有自动排定下一阶段。

## 面试可解释的设计

- 为什么需要事务：避免申请批准了但猫咪未更新，或其他申请未拒绝的半完成状态。
- 为什么锁猫而不是只锁申请：两位工作人员可能同时处理同一只猫的不同申请；它们有不同的申请行，却竞争同一个领养名额。
- 为什么 HTTP 409：请求格式正确，但当前业务状态已不允许这个操作；前端应刷新数据并向使用者解释。
- 为什么关联 DTO 在服务事务内组装：领养、护理时间线和预警队列关闭 open-in-view 后仍能序列化；部分旧接口只在 controller 映射标量字段。
- 为什么演示数据要隔离：复现流程不应依赖或污染开发库，自动测试也应能够反复运行。

当前不应在简历中声称系统具备生产可用身份认证、AI 预测、真实 IoT 部署、高并发性能指标或临床有效性。可以准确描述已实现的领养事务、竞态回归测试、状态一致性和完整的前后端交互。

## 历史验证记录（P2.1）

2026-09-10：P2.1 干净构建的后端全量 25 个测试通过；另行运行的 PostgreSQL V3→V4 与 V4→V5 升级测试均通过，验证后清除了各自的随机测试 schema。P1 时的前端生产构建与 ESLint 通过；P2.1 没有修改前端。浏览器此前已验证提交、审批、申请回执更新，以及移动宽度下的画廊、猫咪详情和预警暂停申请。

本机 Windows 保留了 8080 所在端口段，因此 demo 使用 127.0.0.1:9090，Vite 默认代理同步指向 9090。持久开发的后端默认仍为 8080，切换方法见 README。

## 当前冻结验证

默认 H2 全套 63 项；PostgreSQL 三项迁移检查与三项真实服务事务检查分开运行。后者使用 Flyway UUID schema 与 Hibernate validate，持 Cat 锁并通过 pg_blocking_pids 确认另一事务等待，再验证提交后的结果。前端 build/lint 与 12 项桌面/窄屏护理回归通过。实时 demo 验证与完整结果见 [P2.4b 冻结报告](P2_4B_MILESTONE_FREEZE.md)，可复现命令统一维护在根 README。
