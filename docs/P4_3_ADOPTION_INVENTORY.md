# P4.3 pre-change adoption inventory

Recorded before P4.3 code changes, 2026-09-10. P4.2 changes are present in the working tree and are preserved.

- Entity: AdoptionApplication has id, required lazy Cat, adopterName (120), adopterEmail (200), status, notes, createdAt and updatedAt. There is no account relation. V2 creates the table and Cat FK; V4 adds updatedAt and non-unique status/date and cat/status indexes. V9 creates UserAccount independently. No email uniqueness constraint exists on applications.
- Input: AdoptionApplicationRequest requires catId, adopterName and adopterEmail and accepts optional notes. Name/email are caller-controlled identity. AdoptionService trims name and normalizes email; duplicates use cat + case-insensitive email + PENDING under the Cat lock. No account is consulted.
- Output: AdoptionApplicationResponse and its mapper expose name/email snapshots, cat identity, status, notes and timestamps. Repository review/detail queries fetch Cat for DTO assembly. Review ordering is createdAt DESC, id DESC.
- Service: list(status) is the staff queue; getById(id) has no caller/ownership check; submitApplication(request) binds caller text. approve/reject share Cat locking, final-state guards and competing-application transitions. Those transactions are retained.
- Controller/security: POST /api/adoptions and GET /api/adoptions/{id} are public. GET collection and PATCH approve/reject are STAFF. No owner list endpoint exists. Authenticated writes require CSRF, including public submission by signed-in users.
- Frontend identity uses: ApplicationInput includes name/email; CatDetailPage edits and submits both. ReviewPage displays both and uses name in decision confirmation. ApplicationPage displays name (response also contains email) and polls the receipt every 10 seconds. api.application(id) is the sole frontend receipt read helper.
- Receipt entry paths: successful CatDetail submission navigates to /applications/{id}; ReviewPage links to the same route; saved/direct receipt URLs load ApplicationPage. Its Open staff review link goes to /staff. All receipt reads use GET /api/adoptions/{id}; staff mutations also return the same DTO. There is no My applications route.
- Cache: private staff keys are applications, alerts and health-timeline; receipt uses application/id and currently is not treated as private. Login/logout clear query data, while API 401 clears only the staff keys. P4.3 must also isolate adopter receipt/list data across accounts.
- Test identity uses: AdoptionReviewIntegrationTest submits input name/email, verifies their normalization, duplicate email and receipt DTOs. StaffAuthorizationIntegrationTest explicitly preserves anonymous submission/receipt. TypedCatStatusIntegrationTest, AlertResolutionIntegrationTest and HealthObservationCorrectnessIntegrationTest POST text identities for business fixtures. DemoCareTimelineIntegrationTest, CatLockPostgresRuntimeIT and CatStatusPostgresMigrationIT call submission with text identity. AdoptionFlowIntegrationTest and PostgresMigrationIT directly create historical name/email rows. These last historical fixtures remain useful for NULL-owner compatibility.
- Browser uses: live/milestone.spec.ts fills two names/emails to create competing applications and reads both receipts as STAFF. care/typed-cat-status.spec.ts expects anonymous submission controls; care fixtures and auth-workspace tests supply STAFF auth for staff behavior. No ownership browser tests exist.
- Demo: DemoAccounts provisions one STAFF and one ADOPTER only in the demo profile; DemoData seeds cats/health/care, not applications. Internal IdentityService creates normalized accounts; AccountPrincipal exposes a trusted accountId and role. No registration or claim route exists.

P4.3 classification: POST /api/adoptions becomes ADOPTER; GET /api/adoptions/{id} requires authentication plus STAFF-or-owner service authorization; GET /api/me/adoptions is ADOPTER. Staff review and all care/management rules remain unchanged. Public cat browsing/media remain public. Name/email stay as historical display snapshots, never ownership evidence.
